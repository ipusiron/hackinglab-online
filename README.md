## 📖 基本機能

- 🔍 ツールを分野・カテゴリ・進捗・キーワードで検索
- 📖 書籍・プロジェクトで絞り込み（本のサポートページからの `?book=` リンクで自動的に絞り込み）
- 🧭 絞り込みの条件（書籍・分野・カテゴリ・キーワード）と開いたタブをURLに残す（`?book=`・`?field=`・`?cat=`・`?q=`・`?tab=`。進捗の条件は残さない）。書籍・分野・カテゴリ・タブを選んだあとは、ブラウザーの戻るで1つ前の一覧に戻れる
- 🔗 `#day045`でツール1本のカードへ移動
- 🧩 `?tools=day003,day001,day045`で、選んだ順のツールを最大12本まで共有
- 📄 [JavaScriptなしで読めるツール一覧](https://hackinglab.online/list.html)で、全ツールと書籍ごとの一覧を日英併記
- 📚 学習状況をlocalStorageを使って記録  
- 📊 ダッシュボードで全体進捗＋カテゴリ別・書籍別進捗を可視化  
- 🔗 X（旧Twitter）で進捗を共有し、同じ範囲のリンクをコピー
- 🌐 多言語対応（日本語 / 英語。選んだ言語はこの端末に覚え、`?lang=en` を付けたURLは英語で開く。カードの「使い方 / Usage」は表示言語のREADMEの使い方の節を開く。見出しがない場合は先頭、英語READMEの欠落が確認された場合は日本語版の先頭を開く。英語表示では、GitHub Pages上の「デモ」に`?lang=en`を付ける）

なお、学習プラットフォームとしては最低限の機能しか備えていません。

ランク制やゲーミフィケーション的な機能を実装する予定は今のところありません。

> ランク制を導入してしまうとどうしても他人と比較してしまいがちになります。
> 中級者以降であればそれも刺激になるかもしれませんが、超初心者から初心者まではあまり他人と比較すべきではないと考えているからです。
>
> また、正直なところ現状プラットフォームの運営・改良に私自身が興味が持てないためです。
> そのような時間があれば、多分本を書きまくります。

## 🔄 自動更新フロー（GitHub Actions）

`repos.txt`にツールのGitHub URLを追加すると、各READMEのYAMLマターからカタログを再生成します。
毎週月曜日の6:17（日本時間）にも実行し、READMEの変更を取り込みます。GitHub Actionsの混雑などで開始が遅れる場合があります。

1. 日本語と英語のREADMEをタイムアウト付きで取得する。各ファイルで`main`が404の場合だけ`master`を探す。
2. 登録済みツールの取得やYAML解析に失敗した場合は、前回の有効なデータを残して報告する。前回値のない新規ツールの失敗、IDやslugの重複、不正なURLなどは生成を中止する。
3. カテゴリを日本語、英語の記載順で対応付け、重複するIDを除く。
4. はじめて掲載するIDに日本時間の日付を付け、`data/added.json`と`tools.json`に記録する。以前の日付は書き換えず、非掲載になっても履歴を残す。
5. 静的一覧を作り直し、データ・全カードの描画・静的一覧とデータの一致を検査する。カタログの内容が変わった場合だけ生成日時を更新し、変更のある生成ファイルをコミットする。
6. 最新のmainを取り込んだあとに静的一覧を作り直して再検査し、成功した場合だけpushする。

HTTP 401を受けた場合は、代替ブランチや次のURLへ進まず中止し、生成ファイルも更新しません。
`repos.txt`からの削除や有効な`hub: false`は、意図的な非掲載として反映します。
未知のカテゴリは、`ignored_raw_names`に言語と原文が完全一致するものを除き、実行結果に警告を出します。不正な難易度も警告を出し、値を`null`にします。PRではカテゴリの名前や別名の変更による対応漏れも検査します。

GitHub ActionsのStep Summaryには、ツール総数と掲載数、カタログへの追加・削除、取得失敗や警告などの件数を先に表示し、個別の一覧は折りたたんで表示します。
追加・削除は前回のカタログにあるリポジトリーとの比較です。`hub`による掲載・非掲載の切替は追加・削除に数えません。
デモURLのGET確認は、成功・失敗・URLなしを分けて集計します。確認を実行していない場合は「Not run」と表示します。
デモのHTTP応答は通信の確認であり、ツール内の動作を保証する検査ではありません。

Pagesの公開元（Settings → Pages → Source）はGitHub Actionsです。
[deploy-pages.yml](.github/workflows/deploy-pages.yml)の「Deploy site」が、mainへのpush、mainからの手動実行、または「Update tools.json」の成功後に現在のmainを検査して公開します。
カタログの自動コミットが別のpushワークフローを起動しない場合も、更新処理の成功を受けて公開処理が始まります。

公開前にPythonとNodeのテスト、静的一覧とデータの一致を確認します。
合格したHTML、CSS、JavaScript、データ、画像などの公開用ファイルをまとめ、同じ実行のデプロイ処理へ渡します。
検査に失敗した場合は公開しません。

サイトへの反映は、Actionsで「Deploy site」のbuildとdeployが両方成功したことと、公開URLの内容で確認します。
実際に公開するコミットは、buildのStep Summaryに記録したSHAで確認できます。実行開始のきっかけになったコミットと異なる場合があります。
公開元の設定方法は[GitHubの説明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)を参照してください。

### READMEの使い方リンク

任意の`readme_usage`には、`ja`と`en`の各言語について`{"status":"heading","fragment":"使い方"}`、`{"status":"top"}`、`{"status":"missing"}`のいずれかを保存します。
これはREADME本文から生成する値であり、YAMLマターへの記入は不要です。
`fragment`はURLではなく、符号化前の見出しIDです。
共有リンク関数は検証したGitHubリポジトリに`blob/HEAD/README.md`または`README.en.md`を付け、断片を一度だけ符号化します。
静的一覧も同じ関数で日本語READMEを開き、従来の「GitHub README」表記を保ちます。

日本語READMEの取得やメタデータ解析に失敗した既存ツールは、英語版を取得せず前回のツール全体を保持します。
英語版だけの一時的な失敗では、その言語の有効な前回値だけを保持し、前回値がなければ未確認のままにします。
英語版が両ブランチで404なら`missing`を記録し、日本語版の先頭へ案内します。
取得に成功して使い方見出しが見つからなければ、古い断片を`top`に置き換えます。
メタデータのない旧カタログや不正な任意値でも画面を開けるよう、表示側は要求言語のREADME先頭を使います。

抽出器はコードフェンスやコメントを除き、Markdown見出し、可視テキスト、重複を含む見出しID、使い方の意味に合う見出しの選択を分けて処理します。
GitHubのMarkdown描画全体を再現するものではなく、判定できない構文や処理上限に達した場合はREADMEの先頭へ案内します。
リンク先は更新される`HEAD`なので、次回のカタログ生成までに本文が変われば見出しと一致しなくなることがあります。

### ▶ added.json（自動管理）

`data/added.json`は、`{"day001": "2025-11-24"}`のようにIDと初掲載日を記録します。
日付はmainのカタログで表示対象になった日（日本時間）であり、ツールの制作日や、公開サイトで最初に表示された時刻とは異なります。
既存分はmainのGit履歴から復元し、追加後は説明の変更や再掲載でも日付を変えません。
通常の更新でファイルが欠けたり壊れたりした場合は中止するため、すべてのツールが当日の新着になることを防げます。

### ▶ categories.json（手動管理）

`data/categories.json`の中身の例：

```json
[
  {
    "id": "classic-crypto",
    "ja": "古典暗号",
    "en": "Classical Cryptography",
    "aliases_ja": ["古典的暗号", "クラシカル暗号"],
    "aliases_en": ["Classical cryptography", "Classical Cipher", "classic crypto"]
  },
  {
    "id": "color-theory",
    "ja": "色彩理論",
    "en": "Color Theory"
  }
]
```

`categories.json`の各フィールドは以下の意味を持ちます。

- **id**：識別子（集計・フィルター動作に使用するキー）。絞り込みの URL の `?cat=` にもそのまま出るので、英小文字・数字・ハイフンだけで書く（`npm test` が確かめる）。変えたり消したりしたときは `tools.json` も作り直す。旧 `learning-support` は `machine-learning` へ読み替える。それ以外の未知の id は絞り込みを適用せず、URLから外す
- **ja / en**：画面に表示するカテゴリ名
- **aliases_ja / aliases_en**：表記ゆれを吸収するための別名。`tools.json` を作るときに README のカテゴリー名を `id` へ対応させるのに使い、キーワード検索でもカテゴリー名と同じく探す対象にする

### ▶ category_groups.json（手動管理）

カテゴリ欄を7つの分野に分け、各分野の先頭から分野全体を選べます。
分野全体の件数は、所属カテゴリに含まれるツールを重複なしで数えます。
選択中の分野や説明のあるカテゴリでは、件数の下に説明を表示します。
検索結果が0件のときは、説明を隠して0件の案内を表示します。

`data/category_groups.json`は、`schema_version: 1`、`groups`、`category_descriptions`、`ignored_raw_names`を持ちます。
分野の名前と説明、カテゴリIDの対応、21カテゴリの説明を管理します。
`ignored_raw_names`は、警告に出さない18組の日英名を言語と原文の完全一致で指定します。
新しい未知名をまとめて隠すものではありません。
カテゴリ対応と分野データの型、余分なキー、重複、前後の空白、参照先を、READMEの取得やファイル更新より前に検証します。

分野は`?field=`、個別カテゴリは`?cat=`に記録します。
両方ある場合は有効なカテゴリを優先し、残る分野指定を履歴を増やさずに外します。
書籍、検索、タブ、言語の条件は保持します。
分野データを取得できない場合は、従来の平らなカテゴリ一覧を表示し、解決できない`field`だけを外します。
書籍データと分野データは必須データと同時に取得を始め、必須データの到着後は同時に最大3秒待ちます。

0本のカテゴリは通常の選択肢から隠しますが、有効な`cat`付きURLで選ばれた場合は、その値を解除できるように選択肢を残します。
分野に属さないカテゴリも、ツールがあれば選べます。
たとえば「可視化」は分野の外に残ります。
自動テストはこれらの表示状態と履歴を検査しますが、実際のOSの選択メニューやスクリーンリーダーの読み上げは手動確認の対象です。

### ▶ books.json（手動管理）

書籍・プロジェクトのフィルターの定義です。ツールは `id`（`dayNNN`）で指すので、`tools.json` の `slug` の表記には依存しません。UTF-8・BOMなしで保存します（`tools.json` には触りません）。

`data/books.json`の最小例：

```json
{
  "schema_version": 1,
  "books": [
    {
      "slug": "security-tools-100",
      "kind": "series",
      "title_ja": "「生成AIで作るセキュリティツール100」プロジェクト",
      "title_en": "\"100 Security Tools with Generative AI\" project",
      "label_ja": "ツール100（プロジェクト）",
      "label_en": "Security Tools 100",
      "url": "https://akademeia.info/?page_id=42163",
      "id_range": ["day001", "day100"]
    }
  ]
}
```

主なフィールドは以下の意味を持ちます（必須は `slug`・`kind`・`title_ja`・`title_en`・`label_ja`・`label_en`・`url`、および `ids` か `id_range` の少なくとも一方）。

- **slug**：`?book=` の値。英小文字・数字・ハイフンのみ、40文字以内、全体で一意
- **kind**：`book`（書籍）か `series`（プロジェクト）。プルダウンのグループに使う
- **title_ja / title_en**：正式題名（バナーの見出し）。英語の正式題名がない本は説明的な英題を入れる
- **label_ja / label_en**：プルダウンに出す短い名（表示幅14以下）
- **url**：読者の入口（紹介・サポート・プロジェクトページ）。`https://` で始める
- **ids**：明示の対象ツール（`dayNNN` の配列、昇順。全件が `tools.json` にあること）
- **id_range**：対象の範囲（両端を含む）。`["day101","day200"]` のように書くと、以降 `repos.txt` に足した新ツールが自動で入る
- **relation**：`introduced`（既定）／`related`（本にツールが登場しない関連ツール。`note_ja`・`note_en` が必須）
- **chapters / refs / common_ref**：ツールが本のどこ（章・付録の節）に出るかを示す。`refs` は `{ "dayNNN": [{ "ch": "ch08", "pages": ["123"] }] }` の形。`pages` は任意で、空なら表示しない
- **dashboard**：`false` にすると書籍別進捗の行を出さない（プルダウンと `?book=` では選べる）

章ごとにツールを示す本（`book`）の例：

```json
{
  "slug": "example-book",
  "kind": "book",
  "title_ja": "書名",
  "title_en": "Book title",
  "label_ja": "書名",
  "label_en": "Book title",
  "url": "https://akademeia.info/?page_id=00000",
  "relation": "introduced",
  "ids": ["day017", "day047"],
  "chapters": [
    { "key": "ch02", "label_ja": "第2章", "label_en": "Ch. 2" },
    { "key": "ch08", "label_ja": "第8章", "label_en": "Ch. 8" }
  ],
  "refs": {
    "day017": [{ "ch": "ch02" }, { "ch": "ch08" }],
    "day047": [{ "ch": "ch08", "pages": ["123"] }]
  }
}
```

本を1件足す手順＝①対象の `dayNNN` を調べる ②`ids`（または `id_range`）と、章があれば `chapters`・`refs` を書く ③`npm run build:pages`で静的一覧を作り直す ④`npm test`で検証 ⑤`books.json`と`list.html`を同じPRへ含める。`npm test` が `data/books.json` の構文・`ids` の存在・`refs` の整合などを失敗で止めるので、CI のログだけで直せます。

章の長い題名は、`chapters` の任意の `title_ja`・`title_en` を対で指定します。一覧の章見出し・章ジャンプ・静的一覧では長い題名を使い、カード内の参照には従来の `label_ja`・`label_en` を使います。長い題名がなければ短いラベルに戻ります。章キー、参照、ツールの掲載順は変えません。

本のリンクから狭い画面で開くと、絞り込み欄は閉じて始まります。利用者が選んだ開閉はページ内で保ち、広い画面では常に条件欄を表示します。条件欄へフォーカスを戻す操作では、先に欄を開きます。章・節へのジャンプは全幅で閉じて始まり、同じ本での再描画や言語変更では開閉を保ちます。「章・節の一覧へ」は章ジャンプを開いて見出しへ戻り、URLや履歴を変えません。一覧末尾の「▲絞り込みへ戻る」は、条件欄を開いてヘッダー直下へスクロールし、使える先頭の条件欄へフォーカスします。浮動表示にはせず、有効なセットで条件欄を隠している間はボタンも隠します。

本のバナーの本数は重複しないツール数です。同じツールを複数の章・節に出す場合だけ、実際に表示したカード枚数を注記します。進捗の条件外になって残ったカードも含め、進捗変更・別タブ同期・復元の際にフォーカス中のカードを作り直しません。

未知の本のリンクと本データの取得失敗は、異なる案内を表示します。カテゴリ・検索・進捗の条件は保持し、全件を表示していない場合は全件表示の文を省きます。セット指定（空・未知のみも含む）と単体ツールのリンクを先に解決し、解除された本の案内を復活させません。通知は件数と同じ読み上げ領域を使います。初期表示・履歴移動・言語変更では本の案内を一度伝え、利用者が条件を変えたときは件数または0件の案内を優先します。

なお、書籍やプロジェクトを選んでいるときに共有すると、共有の文は選んだもののツールの数で作られ、URLにも?book=が付きます。

## GitHub Actions共存環境での安全なpush手順

GitHub Actionsがmainに対して自動で`tools.json`などを更新・コミットする構造のために、「ローカルからの手動push」と「Botのpush」が衝突しやすくなっています。
そのため、push前には必ずrebase（＝最新履歴の取り込み）を行ってください。

### ⚠ push前に必ずrebaseを実行すること

手順は以下のとおりです。

1. 作業開始前（任意）

最初に `main` を最新にしておくと安心です。

```bash
$ git switch main
$ git fetch origin
$ git pull --rebase origin main
```

※必須ではありません。
push直前に行う最終同期が本番です。

2. ローカルで編集する

HTML / CSS / JS / READMEなどを自由に編集します。
この段階はGitHub Actionsが動いていても問題ありません。

3. 編集内容をステージングする（git add）

```bash
$ git add .
```

必要に応じてファイル単位でもOKです。

```bash
$ git add README.md
```

4. ローカルにコミットする（git commit）

```bash
$ git commit -m "Update: ○○ の修正"
```

この時点ではローカルmainにのみコミットが存在しています。
この状態は安全です。

5. push直前の必須儀式（最重要）

GitHub Actionsが裏でmainに更新を入れている可能性があるため、pushの直前に必ず最新を取り込みます。

```bash
$ git fetch origin
$ git pull --rebase origin main
```

ここでコンフリクトが起きた場合は、以下のコマンドを実行します。

```bash
$ git rebase --continue
```

6. 安全なpush

```bash
$ git push origin main
``` 

これでnon-fast-forwardエラーやBotの更新との競合を防止できます。

#### 📌 これで防げる問題

これにより次の問題を防げます。

* non-fast-forwardエラー
* GitHub Actionsが生成した自動コミットとの競合
* pushの失敗・履歴の分岐
* mainの破壊（force pushを回避できる）


#### 🧭 なぜ rebase が必要なのか

GitHub Actionsは、あなたのpushに関係なくmainに新しいコミットを追加します。

その間にあなたがローカルで作業してpushしようとすると、ローカルmainとorigin/mainの履歴がズレてpushが拒否されることがあります。

対応策である`git pull --rebase origin main`コマンドを実行すれば、origin/mainの最新履歴を取り込み、あなたのローカルコミットをその後ろに綺麗に並べ直します。
これにより、mainの歴史を壊さず安全にpushできる状態に整えるという効果があります。

## 進捗を選ぶ

各カードの「進捗」は、未着手・学習中・一周完了・定着済みの4段階から直接選ぶ標準の選択欄です。途中の段階を経由せずに変更でき、前の段階にも戻せます。同じツールが複数の章に出る場合は、すべての選択欄を同期します。操作したカードと選択欄は作り直さず、条件外表示・ダッシュボード・別タブ同期・ファイルからの復元にも同じ値を反映します。

## あとで試す

カードの「あとで試す」で、気になるツールを追加・解除できます。進捗の4段階とは別の記録で、「未着手」のまま追加できます。絞り込みの「あとで試す」だけ表示を選ぶと、書籍・カテゴリ・進捗・検索の条件と組み合わせて見返せます。セットURLで開いたときは、ほかの絞り込みと同様にセットを優先します。「あとで試す」の内容や絞り込みは共有URLに含めません。

記録は公開ツールのIDに対応する `later_{dayNNN}` に保存します（`1` が追加、`0` が解除）。同じツールが複数の章にある場合や、別タブで更新した場合も、ボタンの状態を同期します。絞り込んだ一覧で解除したカードは、操作中の位置とフォーカスを保つため、条件外の表示を付けて次の絞り込みまで残します。進捗の全体リセットでは「あとで試す」を消しません。

## 記録の控えと保存できない場合

学習ダッシュボードから、進捗と「あとで試す」をJSONファイルへ控え、対応する形式のファイルから戻せます。ファイルはこのブラウザー内で処理し、サーバーへ送りません。すべて未着手で「あとで試す」も空の場合はファイルを作りません。既存の `progress_{slug}`（0〜3）は引き続き使用し、ファイルでは `dayNNN` をキーにします。

ファイルは `app: "hackinglab-online"`、`schema_version: 2`、UTCの `saved_at`、整数0〜3の値を持つ `progress`、追加したDay番号の配列 `try_later` から成ります。進捗だけの旧形式（`schema_version: 1`）も読み込めます。対象は全公開ツール（`hub: false` を除く）で、本・検索・進捗・あとで試す・セットの絞り込みには依存しません。保存時は進捗1〜3の既知ツールと「あとで試す」の既知IDをDay順に出力します。読込みは64KiB、進捗・あとで試す各1,000項目を上限とし、構造・値・日時を検証します。既知でないDay番号は無視し、それ以外のキーや不正な値は拒否します。同じキーが複数あるJSONは、標準の `JSON.parse` と同じく最後の値を扱います。

進捗は、ファイルの方が進んでいるツールだけを戻します。「あとで試す」は未追加のツールだけを加え、ファイルにないツールも削除しません。確認と結果の本数は、進捗と「あとで試す」で更新するIDの重複を除いた数です。確認は一度で、承諾後に2回のtask待ちを挟んでから、ページ内の値と保存先の最新値を再確認します。確認画面を閉じた直後は別タブの更新がまだ読取りに反映されず、1回の待機でも一部だけが反映されたChromiumでの実測に対応しています。この待機は反映の機会を与えるもので、通知の完了や原子的な処理を保証するものではありません。別タブの変更で不要になった候補は外し、新しい候補は追加しません。保存先を読み直せない項目は永続保存せずページ内へ保持します。複数タブの完全に同時の操作を、ひとまとまりの処理として保証するものではありません。

保存に失敗した値はこのページ内で優先して使い、画面下に一度だけ知らせを出します。閉じた知らせは同じページ内で再表示しません。別タブで保存先が消去されても、まだ保存できていない値は控えへ書き出せるよう残します。通常の進捗変更と全体リセットは、指定した段階へ変更します。「あとで試す」の解除に失敗した値も、同じくページ内で保持してファイルへ反映します。

Nodeの検査は保存拒否・読取り拒否・部分的な書込み失敗・他タブの変更・ファイル検証と復元を実行します。ブラウザーのダウンロードAPIでは開始までを確認でき、保存先への実ファイルの書込み完了やキャンセルは検知できません。「最後に保存した日」は開始が成功した時点の日付です。実機Safariの長期間の保存消去、各OSのファイル選択画面、実スクリーンリーダーでの読み上げは、この自動検査では確認していません。

## 共有する範囲とリンク

書籍やプロジェクトを選んでいないときは、公開中の全ツールの記録を使います。
選んでいるときは、その対象を重複なしで数えます。
カテゴリ・分野・検索・進捗の絞り込みは、共有する本数を変えません。
セットのリンクで開いたときは、全体の記録を共有します。
一周完了か定着済みのツールを「一周した本数」とし、まだないときは数を入れない文にします。

「リンクをコピー」は公開先URLだけをコピーします。
URLに含める条件は選択中の書籍・プロジェクトと英語表示だけで、進捗の値は含めません。
コピーできない場合は、表示された欄を選んで手動でコピーできます。
Xで共有するボタンは投稿画面を開き、実際の投稿は利用者が行います。
